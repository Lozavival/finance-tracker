# Business Rules

This document defines the formal business rules, constraints, and behavioral specifications for the Finance Tracker application. Each rule (`BR-###`) describes required system behavior, including boundary conditions, calculation invariants, validation rules, and error handling.

## Legend

- **ID**: A unique identifier for each business rule (BR-###).
- **Rule Description**: A concise statement of the business rule or constraint being defined, outlining the required behavior or condition.
- **Source**: The location in the codebase where the rule is implemented or enforced.
- **Notes / TODO**: Functional confirmation details, edge case considerations, or automated test coverage references.

## Monetary Arithmetic & Precision

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-001 | All monetary amounts, account balances, budget limits, and credit card usage metrics must be calculated and stored as integer cents to eliminate floating-point rounding errors. | [currency.ts](../src/app/data/currency.ts), [schema.ts](../src/db/schema.ts) | Verified in `tests/unit/data/currency.test.ts`. |
| BR-002 | Transaction amounts must be strictly positive ($> 0$); credit card limits and reference monthly income must be non-negative ($\ge 0$); account opening balances may be positive, zero, or negative integer cents. | [rpcSchemas.ts](../src/server/rpcSchemas.ts), [TransactionFormDialog.tsx](../src/app/components/shared/transaction-dialogs/TransactionFormDialog.tsx) | Note: `serializedTransactionSchema` in `rpcSchemas.ts` currently validates single transaction `value` with `.int()` without `.positive()`; UI enforces $> 0$. |
| BR-003 | Multi-currency conversions between `USD` and `BRL` must multiply or divide by the exchange rate (live rates rounded to 4 decimal places) and round the converted result to the nearest integer cent (`Math.round`); null, zero, non-finite, or negative exchange rates must be rejected and return `null`. | [currency.ts](../src/app/data/currency.ts) | Verified in `tests/unit/data/currency.test.ts`. |
| BR-004 | When the live exchange rate fetcher fails or the device is offline, the system must retain the last confirmed rate or manual override without interrupting transactions, classifying failures into deterministic error codes (`OFFLINE`, `TIMEOUT`, `HTTP_ERROR`, `INVALID_RATE`, `UNKNOWN`). | [currency.ts](../src/app/data/currency.ts), [FinanceContext.tsx](../src/app/state/FinanceContext.tsx) | Verified in `tests/unit/data/currency.test.ts`. |
| BR-005 | When aggregating multi-currency balances or cash flows without a valid exchange rate configured, the system must never sum disparate currencies at a 1:1 ratio; it must either return `null` for consolidated totals (triggering per-currency breakdown views) or exclude unconvertible foreign transactions from single-currency chart series. | [analytics.ts](../src/app/data/analytics.ts), [AccountsPage.tsx](../src/app/features/accounts/AccountsPage.tsx) | Verified in `tests/unit/data/analytics.test.ts`. |

## Installment Plans & Remainder Distribution

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-006 | When splitting a total purchase into $N$ installments ($2 \le N \le 48$), the sum of all installment amounts must exactly equal the total cents ($\sum \text{installments} \equiv \text{totalCents}$), and the total purchase amount must be at least $N \times 1\text{ cent}$. Any remainder cents ($\text{totalCents} \pmod N$) must be allocated to the first installment ($\text{index} = 0$). | [installments.ts](../src/app/data/installments.ts), [TransactionFormDialog.tsx](../src/app/components/shared/transaction-dialogs/TransactionFormDialog.tsx) | Example: \$100.00 / 3 = 1 × \$33.34 + 2 × \$33.33. Verified in `tests/unit/data/installments.test.ts`. |
| BR-007 | Subsequent installment payment dates must preserve the calendar day of the first installment; when a subsequent month has fewer days, the date must clamp to the final calendar day of that month (e.g., Jan 31 $\rightarrow$ Feb 28/29 $\rightarrow$ Mar 31). | [dates.ts](../src/app/data/dates.ts) | Handles standard and leap year variations via `addMonthsClamped`. |
| BR-008 | Multi-month installment purchases are restricted strictly to expense transactions using credit card payment methods; if an installment draft is submitted with a non-credit payment method, the system collapses it into a single transaction for the full amount on the first date. | [TransactionFormDialog.tsx](../src/app/components/shared/transaction-dialogs/TransactionFormDialog.tsx), [FinanceContext.tsx](../src/app/state/FinanceContext.tsx), [sqliteRepository.ts](../src/server/sqliteRepository.ts) | Enforced in UI form visibility and repository `saveTransactionDraft`. |
| BR-009 | On the main transactions view, an installment series is summarized as a single consolidated accrual purchase (installment number marked `-1` with summed value), whereas on individual account ledger and credit card statement views, installments are represented as individual monthly charges. | [transactions.ts](../src/app/data/transactions.ts), [TransactionsPage.tsx](../src/app/features/transactions/TransactionsPage.tsx) | Verified in `tests/e2e/flows/accrual-view.spec.ts`. |
| BR-010 | Deleting any transaction belonging to an installment series must atomically delete all installments sharing the same `installmentGroupId`. | [DeleteTransactionDialog.tsx](../src/app/components/shared/transaction-dialogs/DeleteTransactionDialog.tsx), [FinanceContext.tsx](../src/app/state/FinanceContext.tsx), [sqliteRepository.ts](../src/server/sqliteRepository.ts) | Note: `docs/flows.md` Flow E mentions choosing between single installment or entire series, but codebase strictly deletes the entire `installmentGroupId`. |

## Double-Entry Transfers & Currency Movements

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-011 | Every internal account transfer must atomically create dual reciprocal transaction records sharing a unique `transferId` and system category `transfer`: an outgoing leg (`expense`) on the source account and an incoming leg (`income`) on the destination account. | [transactions.ts](../src/app/data/transactions.ts), [sqliteRepository.ts](../src/server/sqliteRepository.ts) | Verified in `tests/unit/data/transactions.test.ts`. |
| BR-012 | A transfer cannot have both the same source and destination account and the same source and destination currency (`fromAccountId === toAccountId && fromCurrency === toCurrency`); transferring between different currency pockets of the same multi-currency account is permitted. | [TransactionFormDialog.tsx](../src/app/components/shared/transaction-dialogs/TransactionFormDialog.tsx) | Enforced in UI dialog validation. |
| BR-013 | When transferring between accounts or pockets holding different currencies, both send (`value`) and receive (`toValue`) amounts must be positive, and the outgoing transaction description must record the effective exchange rate label formatted as `(<toValue> <toCurrency> @ <value/toValue> <fromCurrency>/<toCurrency>)`. | [transactions.ts](../src/app/data/transactions.ts) | Verified in `tests/e2e/flows/cross-currency-transfer.spec.ts`. |
| BR-014 | Modifying or deleting either leg of a transfer must automatically synchronize or delete the reciprocal leg sharing the `transferId` inside an atomic database transaction, and internal transfers must be excluded from income/expense KPIs, category breakdowns, and monthly budget totals. | [sqliteRepository.ts](../src/server/sqliteRepository.ts), [analytics.ts](../src/app/data/analytics.ts), [goals.ts](../src/app/data/goals.ts) | Atomic SQLite transaction ensures balanced books. |

## Credit Card Billing Cycles & Statements

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-015 | Credit card transactions occurring on or before `closingDay` are assigned to the current month's statement closing date (clamped to month-end); transactions occurring after `closingDay` roll into the subsequent month's billing cycle, with `periodStart` set to the day immediately following the prior cycle's closing date. | [cardStatements.ts](../src/app/data/cardStatements.ts) | Verified in `tests/unit/data/cardStatements.test.ts`. |
| BR-016 | If credit card `dueDay <= closingDay`, the payment due date must roll into the calendar month following the statement closing month (with month-end date clamping), ensuring payment due dates are never recorded prior to statement closing dates. | [cardStatements.ts](../src/app/data/cardStatements.ts) | Example: Closing Day 20, Due Day 5 $\rightarrow$ Statement closes Mar 20, Due Apr 5. |
| BR-017 | A credit card statement period transitions deterministically by comparing `today` against `closingDate` and `dueDate`: `open` when `today <= closingDate`, `closed` when `closingDate < today < dueDate`, and `paid` automatically when `today >= dueDate`. Statement net total is clamped to $\max(0, \text{charges} - \text{credits})$. | [cardStatements.ts](../src/app/data/cardStatements.ts) | Verified in statement closing engine tests. |
| BR-018 | Credit card limit utilization must sum `total` across all non-`paid` statements (`open` and `closed`) for that account, computing available credit as $\max(0, \text{limit} - \text{used})$ and usage percentage as $\min(100, \text{round}((\text{used} / \text{limit}) \times 100))$ (or $0\%$ when limit is $0$). | [cardStatements.ts](../src/app/data/cardStatements.ts), [CardBillSummary.tsx](../src/app/features/accounts/CardBillSummary.tsx) | Displayed on account card bill summary. |
| BR-019 | Individual credit card transactions must not directly deduct from depository account cash ledgers on their purchase dates; instead, each credit card statement generates a single consolidated `card-bill` cash outflow movement (`-stmt.total`) on `stmt.dueDate` (marked `isEstimate: true` while the statement is `open`), and credit card debt is excluded from liquid total balance KPIs. | [ledger.ts](../src/app/data/ledger.ts), [analytics.ts](../src/app/data/analytics.ts) | Verified in `tests/unit/data/ledger.test.ts`. |

## Recurring Rules & Forecasting Horizon

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-020 | Unbounded (`infinite`) recurring rules must be projected forward on a monthly schedule for 24 occurrences (`RECURRING_PROJECTION_MONTHS = 24`) starting from `startDate` using month-end date clamping. | [recurring.ts](../src/app/data/recurring.ts) | Verified in `tests/unit/data/recurring.test.ts`. |
| BR-021 | When a recurring rule specifies a count limit ($N$), exactly $\max(1, N)$ monthly occurrences must be projected starting from `startDate`; rules with start dates in the past count historical occurrences toward the total limit. | [recurring.ts](../src/app/data/recurring.ts) | Enforced in `buildRecurringTransactions`. |
| BR-022 | Canceling a recurring rule sets its status to `canceled` with an effective cutoff date (`canceledAt`) and deletes all projected transactions on or after `canceledAt` while preserving historical occurrences before `canceledAt`. Deleting a recurring transaction from the ledger must offer three scopes: `only-this` (single occurrence), `this-and-future` (cancels rule at transaction date), or `all` (deletes rule and all past/future occurrences). | [recurring.ts](../src/app/data/recurring.ts), [DeleteTransactionDialog.tsx](../src/app/components/shared/transaction-dialogs/DeleteTransactionDialog.tsx), [sqliteRepository.ts](../src/server/sqliteRepository.ts) | Verified in `tests/e2e/flows/recurring-subscriptions.spec.ts`. |

## Account Lifecycle, Ledgers & Deletion Safeguards

| BR-025 | Accounts must restrict allowed payment methods by account kind: `Cash` accounts allow only `cash` and cannot attach a credit card; `Checking` and `Savings` accounts allow only non-cash payment methods (with `Savings` defaulting to `bank-transfer`), and credit card payment methods are permitted only when a credit card configuration is attached to the account. | [settings.ts](../src/app/data/settings.ts), [AccountFormDialog.tsx](../src/app/features/accounts/AccountFormDialog.tsx) | Enforced via `getAllowedPaymentMethodIds` and `AccountFormDialog`. |

## Budget Goals & Financial Alert Engine

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-032 | Each individual budget goal category allocation percentage must be clamped between $0\%$ and $100\%$, and saving the overall budget goal allocations requires the sum of all category percentages to equal $100\%$ within a $\pm 0.05\%$ tolerance (`Math.abs(totalAllocated - 100) < 0.05`); otherwise, saving is blocked with a validation toast. | [GoalsConfigPanel.tsx](../src/app/features/goals/GoalsConfigPanel.tsx), [GoalCategoryDialog.tsx](../src/app/features/goals/GoalCategoryDialog.tsx) | Verified in `tests/components/goals/GoalCategoryDialog.test.tsx` and `tests/e2e/flows/budget-alerts.spec.ts`. |
| BR-033 | Monthly category budget limits must be computed as $\text{round}((\text{budgetBase} \times \text{percentage}) / 100)$, where `budgetBase` is `referenceMonthlyIncome` if $> 0$, falling back to actual month-to-date non-transfer income. Unmapped expense transactions in a month are attributed to the first configured goal category so total categorized spending reconciles. | [goals.ts](../src/app/data/goals.ts) | Verified in `tests/unit/data/goals.test.ts`. |
| BR-034 | A budget warning alert must be generated when MTD category spending reaches the configurable warning threshold ($50\%$–$99\%$, default $85\%$), and upgraded to a critical overspending alert when spending reaches or exceeds $100\%$ of the allocated category budget. | [notifications.ts](../src/app/data/notifications.ts) | Verified in `tests/e2e/flows/budget-alerts.spec.ts`. |
| BR-035 | An upcoming bill alert must be generated for any `open` credit card statement with a positive balance whose payment due date is within 7 calendar days of `today`, with `warning` severity when due in 4–7 days and `critical` severity when due within 3 calendar days (`daysRemaining <= 3`). | [analytics.ts](../src/app/data/analytics.ts), [notifications.ts](../src/app/data/notifications.ts) | Verified in `tests/unit/data/notifications.test.ts`. |
| BR-036 | The heuristic signal engine must also detect: (a) **Multi-Month Budget Streaks** (`warning` at 2 months, `critical` at 3 months when a goal category exceeds its budget across the current and past 2 months); (b) **Spending Velocity Spikes** (`warning` when current-month category spending is $\ge 1.35\times$ the 3-month rolling average and baseline average is $\ge 4,000$ cents); and (c) **Net Cash Flow Signals** (`success` savings milestone when monthly savings rate is $\ge 25\%$, or `critical` deficit warning when net monthly savings is $< 0$). | [analytics.ts](../src/app/data/analytics.ts) | Verified in `tests/unit/data/analytics.test.ts`. |
| BR-037 | Both the top navigation `NotificationCenter` and the dashboard `SmartInsightsContent` panel must derive active alerts exclusively from `useFinancialAlerts()`, deduplicating by period key, filtering out disabled alert kinds (except `system` offline alerts) and user-dismissed alerts, and sorting by descending severity (`critical` > `warning` > `info` > `success`). | [notifications.ts](../src/app/data/notifications.ts), [useFinancialAlerts.ts](../src/app/state/useFinancialAlerts.ts) | Verified in `tests/unit/hooks/useFinancialAlerts.test.tsx`. |

## Full-Text Search & Text Normalization

| ID | Rule Description | Source | Notes / TODO |
| ---- | ------------------ | -------- | -------------- |
| BR-038 | The full-text search index `transactions_fts` (SQLite FTS5 with trigram tokenizer) must be maintained exclusively via database triggers across insert, update, and delete operations and synchronized on database initialization; manual direct writes to `transactions_fts` from application logic are forbidden. | [client.ts](../src/db/client.ts) | Verified in `tests/integration/db/fts-triggers.test.ts`. |

| BR-040 | Full-text search queries execute read-only against the global database without mutating the repository's 90-day loaded transaction window (`loadedFromDateStr`), ordering results with past/today transactions first (newest first) followed by future transactions (soonest first), and collapsing recurring rules, installment series, and transfers into representative groups in the global search preview. | [search.ts](../src/app/data/search.ts), [sqliteRepository.ts](../src/server/sqliteRepository.ts) | Read-only search invariant verified in integration tests. |
